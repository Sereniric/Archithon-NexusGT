# 2. FEATURE ONE: EXPLAINABLE PRIVACY RISK ASSESSMENT

## Objective

Create a deterministic risk assessment engine that evaluates the privacy implications of an application's declared permissions and existing analysis findings.

The engine must explain WHY something deserves attention instead of simply producing a numerical score.

Create:

```text
backend/
└── analyzer/
    └── risk_analyzer.py

backend/
└── knowledge_base/
    └── risk_rules.json

backend/
└── tests/
    └── test_risk_analyzer.py
```

## A. Assessment dimensions

Evaluate three separate dimensions.

### 1. Permission Exposure

Assess the sensitivity of recognized declared permissions.

Consider:
- Access to location.
- Camera access.
- Microphone access.
- Contacts access.
- Call-related information.
- SMS-related information.
- Photos and media.
- Storage.
- Other sensitive capabilities already represented in the knowledge base.

Use the existing permission knowledge base as the source of permission information.

Do not invent permission classifications.

Do not assume every declared permission is actively used.

### 2. Application Purpose Alignment

Use the existing `app_purpose_analyzer.py` output.

Consider its existing classifications:

- Potentially relevant.
- Needs review / unclear.
- No clear relationship identified.

Use these classifications as evidence for review prioritization.

Do not create new unsupported conclusions.

### 3. Privacy Transparency

Use the existing policy analysis and permission-policy comparison results.

Consider:
- Relevant policy coverage found.
- No relevant policy statement found.
- Unknown / cannot determine.
- Missing privacy topics.

Missing disclosure must be treated as a transparency gap, not proof of privacy violations.

## B. Scoring model

Implement a transparent, configurable scoring model.

Use a 0–100 scale where higher values mean more findings require review.

Important:
- This is a review-priority score, NOT a probability of malicious behavior.
- Every score must have a documented calculation.
- Weights and rules must be stored in `risk_rules.json`.
- Avoid arbitrary hardcoded scoring scattered across Python functions.
- Keep scoring deterministic.
- Use a documented approach to avoid double-counting the same permission across multiple findings.
- Separate permission exposure, purpose alignment and transparency results.
- Unknown permissions must remain unknown. Do not invent a risk value for them.
- Missing information must not silently be treated as safe.
- Do not let one missing privacy-policy statement automatically produce an extreme overall score.

If the available evidence is insufficient, return an appropriate "Insufficient evidence" or "Limited assessment" status instead of pretending the score is reliable.

## C. Risk assessment output

Return a structured result containing:

- Overall review-priority score, if calculable.
- Assessment status.
- Permission exposure assessment.
- Purpose alignment assessment.
- Transparency assessment.
- Findings requiring attention.
- Evidence supporting every finding.
- Explanation of why each finding matters.
- Scoring methodology and limitations.

Each finding should contain, where applicable:

- Finding title.
- Related permission identifier.
- Severity or review priority.
- Explanation.
- Evidence source.
- Supporting policy excerpt, if applicable.
- Reason for the assessment.

Keep the exact permission identifiers.

Never generate unsupported findings.

## D. Recommendations

Provide deterministic recommendations based on existing findings.

Examples:
- Review whether sensitive permissions are necessary for the stated application purpose.
- Check whether location collection is adequately explained in the supplied privacy policy.
- Investigate unfamiliar permissions before release.
- Review permissions that have no clear relationship with the declared application purpose.

Recommendations must be relevant to actual findings.

Do not make generic recommendations unrelated to the analyzed application.

# 3. FEATURE TWO: PRIVACY NUTRITION LABEL

## Objective

Create a user-friendly summary of the application's declared permission capabilities.

Normal users should be able to understand the privacy implications without knowing Android permission identifiers.

Create:

```text
backend/
└── analyzer/
    └── nutrition_label.py

backend/
└── tests/
    └── test_nutrition_label.py
```

## A. Permission categories

Use the existing permission knowledge base to group recognized permissions into understandable categories.

Suggested categories:

1. Location.
2. Camera and Microphone.
3. Contacts and Personal Information.
4. Phone and Communication.
5. Photos, Media and Storage.
6. Device Information.
7. Network and Connectivity.
8. Other Sensitive Capabilities.

Inspect the actual knowledge base before mapping permissions.

Only assign a permission to a category when the mapping is supported by its existing information.

Unknown permissions must be shown in a separate category:

"Unrecognized Permissions"

Do not guess their purpose.

## B. Nutrition label output

Generate a structured label containing:

- Application name, if provided.
- Total declared permissions.
- Number of recognized permissions.
- Number of unknown permissions.
- Categories detected.
- Permissions belonging to each category.
- Plain-language category explanations.
- Relevant privacy-policy coverage, where available.

Each category must indicate whether corresponding permissions were:

- Declared in the manifest.
- Not detected in the manifest.
- Unknown / cannot determine.

IMPORTANT:

"Not detected" means the corresponding permission was not found in the analyzed manifest. It does NOT prove that the application cannot access the relevant information through other mechanisms.

Do not describe declared permissions as proof that the app actually collects or transmits data.

## C. Consumer and developer detail

The nutrition label must support two levels of information:

### Consumer view
- Simple category names.
- Understandable explanations.
- Clear descriptions of what the application may be capable of accessing.
- Easy-to-read status indicators.

### Developer view
- Exact Android permission identifiers.
- Permission descriptions.
- Protection levels, where available.
- Technical details from the existing knowledge base.
- Supporting analysis evidence.

Do not duplicate the permission knowledge base.
